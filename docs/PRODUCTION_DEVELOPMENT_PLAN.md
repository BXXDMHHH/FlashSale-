# FlashSale 生产开发设计文档

> 文档状态：V1.0 设计基线（待评审）  
> 项目形态：Android 用户端 + Spring Boot 后端 + Vue 3 管理端  
> 架构策略：模块化单体、领域驱动设计（DDD）、REST API  
> 说明：本文定义目标设计和验收标准，不代表功能已经实现。依赖版本应在初始化工程时锁定并通过 CI 验证。

## 1. 项目目标

FlashSale 是一个面向秒杀场景的商城 MVP。用户通过 Android App 浏览商品和秒杀活动、提交抢购、完成模拟支付、查询订单；管理员通过 Vue Web 管理端维护商品、活动、库存配置和业务记录；Spring Boot 后端是唯一可信业务入口。

### 1.1 V1.0 交付范围

- Android：登录、活动列表、活动详情、抢购、订单列表/详情、模拟支付、结果反馈。
- 管理端：管理员登录、商品 CRUD、活动创建与发布、活动库存额度配置、活动状态查看、订单查询、操作审计查询。
- 后端：身份认证与授权、商品、秒杀活动、活动库存、订单、模拟支付、超时关闭、幂等、审计、健康检查。
- 数据：关系型数据库持久化；数据库迁移脚本纳入版本控制。
- 测试：领域规则、接口、事务/并发、安全与端到端验收测试。
- 部署：提供本地开发、测试环境和单实例生产部署说明。

### 1.2 V1.0 不做

- 真实支付渠道、退款、分账。
- 多商家结算、购物车、优惠券、复杂营销。
- 物流、售后、复杂会员等级。
- 首版微服务拆分、分布式事务框架、跨区域多活。
- 把 Redis 作为唯一库存真相来源。
- 未经压测验证就承诺具体吞吐量或可用性指标。

## 2. 系统架构

    Android App (Kotlin + Jetpack Compose)
                     |
                     | HTTPS / REST / JSON
                     v
    Spring Boot API (Java, modular monolith)
      ├── identity       身份认证与权限
      ├── catalog        商品
      ├── promotion      秒杀活动
      ├── inventory      活动库存与库存流水
      ├── ordering       订单与超时关闭
      ├── payment        模拟支付
      └── audit          业务审计

            (建议 MySQL 8.x)
                     ^
                     |

### 2.1 架构决策

- V1 使用模块化单体：一个后端应用、一个关系型数据库，按领域模块组织代码。
- Android 和 Vue 仅展示状态、收集输入；价格、库存、活动资格、订单状态与支付结果均由服务端判断。
- 同步核心流程优先使用数据库事务。不要为了“看起来先进”提前引入微服务和消息队列。
- Redis 可在后续用于缓存、限流或非权威加速；任何缓存都不能绕过数据库库存约束。
- 所有外部请求使用 DTO，不直接暴露数据库实体或领域聚合对象。
- API 采用统一响应格式、错误码、分页规范和请求追踪 ID。

### 2.2 建议技术基线

| 层 | 建议技术 |
|---|---|
| Android | Kotlin、Jetpack Compose、ViewModel、Coroutines、Retrofit/OkHttp、单元测试 |
| Backend | Java 21 LTS、Spring Boot 3.x、Spring Security、Bean Validation |
| Persistence | MySQL 8.x、Flyway、Spring JDBC 或 MyBatis；优先选一种主要持久化方式 |
| Admin Web | Vue 3、TypeScript、Vite、Vue Router、Pinia、Element Plus |
| API contract | REST/JSON、OpenAPI 3 |
| Build/quality | Gradle（Android/Backend 按各自工程配置）、npm/pnpm、JUnit 5、Testcontainers（可选） |
| Deployment | Docker Compose 用于开发/测试；生产环境需配置 HTTPS、密钥、备份和监控 |

以上是推荐基线，不是已经存在的工程依赖。初始化工程时应选择兼容的稳定版本并锁定版本号。

## 3. 业务规则基线

### 3.1 商品与活动

1. 商品必须处于已发布、可售状态，才可创建或发布秒杀活动。
2. 活动包含商品 ID、秒杀价、开始时间、结束时间、库存分配量、限购规则和生命周期状态。
3. 活动有效时间为 startTime <= serverNow < endTime，统一采用服务端时间和明确的时区策略。
4. 活动状态建议：草稿、待开始、进行中、已结束、已取消。时间判断与持久化状态应共同使用，不能只信任前端状态。
5. 活动进入待开始后，不允许直接修改商品、秒杀价、库存额度和起止时间；需要先按规则取消/终止并处理关联订单，再重新创建活动。
6. 商品被下架时，必须定义活动处理策略。建议阻止新的抢购请求；已创建订单按既定订单规则处理，不可无记录地改变订单状态。

### 3.2 活动库存

每个活动有独立库存池。库存数量定义：

**initialQuantity = availableQuantity + reservedQuantity + soldQuantity**

releasedQuantity 是累计释放的审计指标，不应重复加入上面的数量等式。

- 创建待支付订单时：可售 -1、预占 +1、已售不变。
- 支付确认时：预占 -1、已售 +1、可售不变。
- 订单关闭时：预占 -1、可售 +1、已售不变。
- 所有数量不得为负；库存变更必须能关联业务原因和幂等操作标识。
- 同一订单最多释放一次、最多确认销售一次。
- 不允许活动库存额度被多个活动重复分配。V1 不支持其他销售渠道绕过活动库存分配。
- 库存流水记录变更前后数量、变更量、原因、活动 ID、订单 ID、操作/事件 ID、发生时间。

### 3.3 下单与限购

只有满足以下条件才允许创建订单：

- 用户有效且已认证。
- 商品已发布可售，活动符合状态和时间规则。
- 活动库存充足。
- 用户符合活动限购规则。
- 同一用户同一活动不存在另一笔待支付订单。
- 同一用户同一活动最多一件已支付商品（V1 默认规则，可由产品决策调整）。

幂等请求和限购是两个不同问题：

- 相同幂等键重试：返回原请求结果，不重复创建订单。
- 不同幂等键并发下单：仍需由数据库约束/事务规则保证用户限购。

关闭订单后，用户可以重新购买，但必须重新校验活动、库存和限购规则。

### 3.4 订单与支付

- 订单状态：PENDING_PAYMENT、PAID、CLOSED。
- 创建订单时保存商品名称、秒杀单价、数量、金额、活动 ID 等快照；商品后续改名或改价不影响历史订单。
- 支付截止时间固定为创建时间 + 15 分钟，不因查询、重试或重复任务延长。
- 合法状态转换：
  - PENDING_PAYMENT -> PAID：服务端确认合法支付结果，且符合截止时间规则。
  - PENDING_PAYMENT -> CLOSED：用户合法取消或超时关闭。
  - PAID -> PAID：重复支付通知幂等返回，不重复变更库存。
  - CLOSED -> CLOSED：重复关闭幂等返回，不重复释放库存。
  - CLOSED -> PAID：V1 禁止直接转换；迟到的外部支付结果在未来接真实支付时必须进入对账/补偿流程。
  - PAID -> CLOSED：普通关闭拒绝；V1 不做退款。
- 模拟支付也必须由后端验证订单、截止时间和支付尝试状态；客户端不能直接将订单标记为已支付。
- 支付与关闭竞争时，采用条件更新或乐观锁，只有一个合法状态转换成功。

### 3.5 权限与审计

- 用户只能读取自己的订单；订单 ID 不等于访问授权。
- 管理端所有写操作必须有明确角色权限；未来支持商家时，还要校验商家对商品/活动的资源授权。
- 审计记录至少包括操作人、操作类型、目标资源、发生时间、前后状态、结果、原因、幂等/关联 ID。
- 禁止在日志中记录密码、访问令牌、支付凭证或其他敏感认证材料。

## 4. DDD 领域模型与聚合边界

聚合边界由必须共同维护的业务不变量决定，不按数据库表数量、页面数量或微服务数量决定。

### 4.1 Product 聚合

**聚合根：Product**

职责：商品基础信息、发布/下架状态；校验商品自身的状态转换和字段约束。

不负责：活动库存数量、订单价格快照、支付状态。

### 4.2 FlashSaleActivity 聚合

**聚合根：FlashSaleActivity**

职责：商品引用、秒杀价格、开始/结束时间、活动生命周期、限购配置；提供活动是否允许购买的领域判断；保护活动配置不可被非法修改。

活动通过 productId 引用商品，通过 activityId 关联库存，不把整个 Product 或库存历史集合嵌入活动聚合。

### 4.3 FlashSaleInventory 聚合

**聚合根：FlashSaleInventory**，业务维度为 activityId。

职责：可售、预占、已售数量及库存不变量；预占、确认销售、释放预占等合法变更；通过库存流水提供可追溯性。

并发安全必须落实到数据库层。推荐在事务中执行条件更新，例如仅当 available_quantity >= requested_quantity 时扣减，并检查受影响行数；也可使用经测试的乐观锁方案。禁止仅依赖应用内的库存判断。

库存流水不应作为无限增长的内存集合放进聚合对象；流水可以独立持久化，并通过活动 ID、订单 ID 和操作 ID 关联。

### 4.4 Order 聚合

**聚合根：Order**

职责：订单快照、金额、所有者、截止时间；订单状态转换和支付资格判断；不允许应用服务或 Controller 直接任意修改状态字段。

订单引用 userId、activityId 和商品快照，不嵌入整个用户、活动或库存聚合。

### 4.5 PaymentAttempt 候选聚合

支付尝试有独立标识、尝试状态和幂等结果。V1 可以先将其作为支付模块中的领域实体/记录；当支付尝试拥有独立生命周期、不变量或多渠道处理需求时，再正式划为独立聚合。

支付模块不能绕过 Order 聚合的状态转换规则。支付确认由应用服务协调支付结果、订单状态和库存确认。

### 4.6 Identity / Authorization

身份认证、角色和资源授权属于独立模块。V1 可采用简单角色权限；不要为了套用模板而过度设计复杂 RBAC。订单所有权校验必须在服务端完成。

### 4.7 聚合间协作

- 聚合之间优先通过 ID 引用，不持有其他聚合的完整对象。
- 领域规则放在领域对象/领域服务中；跨聚合用例由应用服务协调。
- 领域事件可用于表达事实，但 V1 不要求为了每个操作引入消息中间件。
- 聚合边界不等于事务边界：同一个用例可以在应用服务中通过一个数据库事务协调多个聚合。

## 5. 后端模块与代码组织

建议按业务领域分包，而不是把所有 Controller、Service、Mapper 分别放入全局大包。

    backend/
      src/main/java/.../flashsale/
        identity/{api,application,domain,infrastructure}
        catalog/{api,application,domain,infrastructure}
        promotion/{api,application,domain,infrastructure}
        inventory/{api,application,domain,infrastructure}
        ordering/{api,application,domain,infrastructure}
        payment/{api,application,domain,infrastructure}
        audit/{api,application,domain,infrastructure}
        shared/{config,error,web,observability}
      src/main/resources/db/migration/
      src/test/java/...

层职责：

- api：Controller、请求/响应 DTO、参数校验；不写业务事务逻辑。
- application：用例编排、事务边界、权限校验、幂等处理。
- domain：聚合、值对象、领域规则、领域事件；不依赖 Web 框架和数据库 Mapper。
- infrastructure：数据库实现、外部适配器、持久化映射。
- shared：只放真正跨模块的基础设施，不成为无边界的公共业务包。

## 6. 数据库设计建议

金额使用 DECIMAL 或以最小货币单位整数存储，禁止使用浮点数表示货币。

### 6.1 核心表

| 表 | 关键字段/约束建议 |
|---|---|
| users | id、登录标识唯一、密码哈希、状态、创建时间 |
| roles / user_roles | 角色与用户关系；V1 可简化 |
| products | id、名称、描述、图片引用、状态、版本、时间戳 |
| flash_sale_activities | id、product_id、秒杀价、开始/结束时间、状态、限购配置 |
| flash_sale_inventory | activity_id 唯一、初始/可售/预占/已售数量、版本 |
| orders | 订单号唯一、用户 ID、活动 ID、商品快照、单价、数量、金额、状态、截止时间 |
| payment_attempts | 尝试 ID、订单 ID、幂等标识、状态、结果、时间戳 |
| inventory_transactions | 活动 ID、订单 ID、变更类型、数量变化、前后数量、操作 ID、时间 |
| idempotency_records | 用户/作用域/幂等键唯一、请求摘要、结果引用/状态、创建时间 |
| audit_logs | 操作人、操作、目标、前后状态、结果、关联 ID、时间 |

### 6.2 约束与索引

- 主键和业务唯一键必须由数据库约束兜底。
- orders.order_no 唯一。
- 幂等记录使用适合业务范围的唯一键，例如 (user_id, scope, idempotency_key)。
- 库存表对 activity_id 建唯一约束；数量字段设置非负约束（若所选数据库支持并正确执行）。
- 对活动状态/开始时间、用户订单查询、订单状态/支付截止时间建立经查询计划验证的索引。
- 用户限购不能只依赖“先查后插”。需要在事务、锁策略和必要的唯一约束中实现；若数据库不能用简单唯一索引表达“待支付或已支付”的组合条件，应设计购买资格/占用记录或经验证的锁方案。
- 库存流水与订单状态变更应在同一事务中记录，或设计可靠的事件/outbox 方案，避免业务成功却没有审计记录。

## 7. 核心用例与事务设计

### 7.1 创建抢购订单 PlaceOrder

建议流程：

1. 校验登录身份和请求格式。
2. 以用户、业务作用域和幂等键检查重复请求；校验同一键的请求摘要一致。
3. 读取并校验活动、商品状态和服务端时间。
4. 在事务中竞争用户限购资格，确保同用户不同请求也无法创建多笔待支付订单。
5. 使用数据库原子条件更新预占活动库存。
6. 创建待支付订单，固定商品/价格快照与 paymentDeadline = createdAt + 15 minutes。
7. 写库存流水和幂等结果。
8. 提交事务并返回订单信息。

上述步骤的读写顺序可根据具体锁方案调整。关键要求是库存预占、订单创建、限购占用、必要流水与幂等结果具有可证明的一致性；任何失败不得遗留无主预占。相同请求在提交成功但响应超时时重试，必须能找回原结果。

**V1 推荐：**订单和库存位于同一个关系型数据库，使用单个本地数据库事务协调。不要先扣库存再依赖不可靠的异步建单。

### 7.2 支付确认 ConfirmPayment

1. 校验支付尝试、订单归属和服务端支付规则。
2. 对支付尝试和订单执行幂等校验。
3. 以条件更新/锁保护订单从待支付到已支付的唯一转换，并检查截止时间。
4. 在同一事务内将库存预占转为已售，写库存流水，保存支付结果。
5. 若订单已支付，重复确认返回幂等结果，不重复改库存。
6. 若订单已关闭，拒绝直接改成已支付；未来接入真实支付时应进入异常支付对账流程。

### 7.3 关闭订单 CloseOrder

- 用户取消和超时任务调用同一套领域关闭规则。
- 仅待支付订单可关闭。
- 使用条件更新或锁确保订单只关闭一次。
- 在同一事务中释放预占库存、写库存流水并记录关闭原因。
- 重复关闭返回既有结果，不重复释放库存。
- 定时任务必须可重复运行；不能假设任务只执行一次。

### 7.4 订单超时任务

V1 可采用 Spring 定时任务分批扫描到期的待支付订单。扫描必须有合适索引，批量处理应控制事务大小。多实例运行时需使用安全的抢占/锁定方式，避免同一订单被并发重复处理；即使重复处理，业务操作仍必须幂等。

## 8. REST API 契约草案

统一前缀：/api/v1

统一成功响应建议：

    {
      "code": "OK",
      "message": "success",
      "data": {},
      "traceId": "..."
    }

统一错误响应建议：

    {
      "code": "OUT_OF_STOCK",
      "message": "活动库存不足",
      "data": null,
      "traceId": "..."
    }

### 8.1 Android 用户端

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /auth/login | 登录并取得访问凭证 |
| GET | /products | 浏览可售商品 |
| GET | /activities | 浏览秒杀活动，支持分页/状态筛选 |
| GET | /activities/{activityId} | 活动详情 |
| POST | /activities/{activityId}/orders | 抢购；要求幂等键 |
| GET | /orders | 当前用户订单分页列表 |
| GET | /orders/{orderId} | 查询自己的订单 |
| POST | /orders/{orderId}/cancel | 取消待支付订单 |
| POST | /orders/{orderId}/payment-attempts | 创建模拟支付尝试 |
| POST | /payment-attempts/{attemptId}/simulate-confirm | V1 测试用途的模拟支付确认 |

模拟支付确认接口必须明确仅用于 V1 演示/测试环境，并由后端执行校验；生产环境不应提供任何可被任意客户端利用的“伪造成功”入口。若产品要在真实生产环境展示模拟支付，应限制为明确的演示模式和受控账户。

### 8.2 Vue 管理端

| 方法 | 路径 | 说明 |
|---|---|---|
| GET/POST | /admin/products | 商品列表/创建 |
| GET/PATCH | /admin/products/{id} | 商品详情/修改 |
| POST | /admin/products/{id}/publish | 发布商品 |
| POST | /admin/products/{id}/unpublish | 下架商品 |
| GET/POST | /admin/activities | 活动列表/创建 |
| GET | /admin/activities/{id} | 活动详情 |
| POST | /admin/activities/{id}/publish | 发布活动 |
| POST | /admin/activities/{id}/cancel | 取消活动（必须校验关联订单/库存） |
| GET | /admin/orders | 订单查询 |
| GET | /admin/inventory/{activityId} | 活动库存与库存流水 |
| GET | /admin/audit-logs | 审计查询 |

所有管理接口必须做服务端角色校验；活动取消不能只更新状态而忽略预占库存和未支付订单。

API 路径与字段是契约草案。正式开发前需用 OpenAPI 固化请求 DTO、响应 DTO、错误码、分页参数和权限要求。

## 9. 统一错误码建议

| 错误码 | 含义 |
|---|---|
| UNAUTHENTICATED | 未登录/凭证无效 |
| FORBIDDEN | 无权访问资源 |
| RESOURCE_NOT_FOUND | 资源不存在或不可见 |
| PRODUCT_NOT_SELLABLE | 商品不可售 |
| ACTIVITY_NOT_STARTED | 活动未开始 |
| ACTIVITY_ENDED | 活动已结束 |
| ACTIVITY_CANCELLED | 活动已取消 |
| OUT_OF_STOCK | 库存不足 |
| DUPLICATE_PENDING_ORDER | 已存在待支付订单 |
| PURCHASE_LIMIT_EXCEEDED | 超出限购规则 |
| IDEMPOTENCY_KEY_CONFLICT | 同一幂等键对应不同请求内容 |
| ORDER_EXPIRED | 订单已过支付期限 |
| ORDER_ALREADY_CLOSED | 订单已关闭 |
| INVALID_ORDER_STATE | 当前订单状态不允许该操作 |
| PAYMENT_REJECTED | 支付确认不合法 |
| VALIDATION_ERROR | 请求参数不合法 |
| INTERNAL_ERROR | 未预期服务端错误 |

错误响应不能泄露 SQL、堆栈、密钥或其他内部敏感信息。

## 10. Android 客户端设计

建议结构：

    android/
      app/
      core/network/
      core/model/
      core/ui/
      feature/auth/
      feature/activitylist/
      feature/activitydetail/
      feature/checkout/
      feature/orders/
      data/repository/
      data/remote/

- Compose UI 只负责展示状态和用户交互。
- ViewModel 管理界面状态，通过 Repository 调用 API。
- 不在客户端计算权威库存、秒杀资格、最终金额或支付状态。
- 抢购按钮应防止重复点击，但后端仍必须做幂等和并发保护。
- 明确处理加载中、网络错误、活动未开始、库存不足、已抢到、订单过期等状态。
- Token 安全保存，不写入日志；网络请求配置超时和合理重试策略。创建订单请求重试必须复用同一个幂等键。
- 测试覆盖 ViewModel 状态转换、Repository 映射、关键页面流程和服务端错误展示。

## 11. Vue 管理端设计

建议结构：

    admin-web/
      src/api/
      src/components/
      src/layouts/
      src/router/
      src/stores/
      src/views/login/
      src/views/products/
      src/views/activities/
      src/views/orders/
      src/views/inventory/
      src/views/audit/
      src/types/

- TypeScript 开启严格类型检查。
- API 请求统一封装 token、错误处理、超时和 traceId。
- 路由守卫仅改善用户体验，真正的权限必须由后端验证。
- 删除、下架、取消活动等危险操作必须有确认交互。
- 活动库存显示可售、预占、已售、累计释放和对账状态；不要只显示一个“库存”数字。
- 管理端不得直接写数据库或绕过业务 API。
- 对表格实现分页、筛选、空状态、加载状态和接口错误状态。

## 12. 安全基线

- 只使用 HTTPS 部署；本地开发可使用 HTTP。
- 密码使用成熟密码哈希算法（如 BCrypt/Argon2），不明文保存。
- 使用 Spring Security 实现认证与授权；访问凭证生命周期和刷新策略应在实现前确定。
- 对所有用户资源实施所有权校验，避免 IDOR。
- 登录、下单和模拟支付接口设置速率限制与审计。
- 管理端写操作采用最小权限原则。
- 使用环境变量或密钥管理存储数据库密码、签名密钥等，不提交到 Git。
- CORS 仅允许明确的管理端来源；不能用通配来源配合凭证。
- 校验请求 DTO、限制分页最大值、限制图片上传类型和大小（若支持上传）。
- 生产环境关闭调试端点和详细异常输出。
- 依赖升级和漏洞扫描纳入 CI。

## 13. 测试与验收

### 13.1 领域单元测试

- 活动时间边界：开始时刻可购买，结束时刻不可购买。
- 活动非法状态转换被拒绝。
- 库存不能变成负数，库存等式保持成立。
- 订单非法状态转换被拒绝。
- 支付截止时间创建后固定。
- 同一订单重复关闭、重复支付确认不会重复产生业务效果。

### 13.2 集成与并发测试

| 编号 | 场景 | 预期结果 |
|---|---|---|
| TC-01 | 活动未开始抢购 | 拒绝；库存不变 |
| TC-02 | 活动已结束抢购 | 拒绝；库存不变 |
| TC-03 | 20 件库存成功预占 20 次 | 可售 0、预占 20、已售 0 |
| TC-04 | 第 21 次抢购 | 库存不足 |
| TC-05 | 100 个并发请求抢最后一件 | 最多一个预占成功 |
| TC-06 | 同用户并发重试同一幂等请求 | 只创建一笔订单并返回同一结果 |
| TC-07 | 同用户用不同幂等键并发下单 | 限购规则仍成立 |
| TC-08 | 预占后订单创建失败 | 整体回滚，不留无主预占 |
| TC-09 | 支付成功 | 预占 -1、已售 +1 |
| TC-10 | 重复支付确认 | 不重复确认，不重复改库存 |
| TC-11 | 订单超时关闭 | 预占 -1、可售 +1 |
| TC-12 | 重复关闭订单 | 库存只释放一次 |
| TC-13 | 支付与关闭并发 | 只有一个合法终态转换成功，库存匹配最终状态 |
| TC-14 | 关闭后重新抢购 | 重新校验活动、库存和限购 |
| TC-15 | 用户访问他人订单 | 拒绝访问 |
| TC-16 | 库存对账 | 数量等式成立且每次变化可追溯 |

并发测试必须使用真实数据库或接近生产的测试数据库验证，不能只用 Mock 测试代替数据库竞争测试。

### 13.3 端到端验收

1. 管理员创建商品并发布。
2. 创建活动，分配活动库存并设置未来开始时间。
3. Android 用户浏览活动；活动未开始时无法抢购。
4. 活动开始后成功抢购，订单显示待支付。
5. 模拟支付成功，订单变为已支付，库存从预占转为已售。
6. 另一笔订单不支付，超过 15 分钟后关闭并释放库存。
7. 管理端能查看订单、库存流水和审计记录。
8. 未授权用户无法调用管理接口；用户无法查看其他人的订单。

## 14. 可观测性与运维

- 结构化日志包含 traceId、操作类型、资源 ID、结果码；不得记录密码、Token 和敏感凭证。
- 暴露健康检查、应用版本和基本运行指标；管理端不可访问不必要的内部运维信息。
- 重点监控下单成功/失败率、库存不足比例、数据库连接池、事务冲突、订单超时关闭失败、支付幂等冲突。
- 定期备份数据库，并演练恢复。
- 数据库迁移必须可审查、可重复部署；生产升级前先备份并验证回滚/前向修复方案。
- 生产部署需配置 TLS、访问控制、日志轮转、资源限制、告警与恢复责任人。

## 15. 开发阶段与交付物

### Phase 0：工程基线
- 建立 backend/、android/、admin-web/ 工程。
- 确定 Java/Kotlin/Node 版本和依赖锁定方式。
- 建立代码格式化、静态检查、测试和 CI。
- 输出：可构建的空工程、开发环境说明、API/OpenAPI 初稿。

### Phase 1：身份与商品
- 登录/权限、商品管理、基础浏览。
- 输出：迁移脚本、接口测试、Android 商品列表、Vue 商品管理。

### Phase 2：活动管理
- 活动创建、发布、时间规则、库存额度初始化。
- 输出：活动领域测试、管理端活动流程、活动查询 API。

### Phase 3：库存与下单
- 库存聚合、条件更新、幂等、限购、订单快照、单事务建单。
- 输出：并发测试、库存流水、TC-01 至 TC-08。

### Phase 4：支付与关闭
- 模拟支付、订单状态机、超时任务、库存确认/释放。
- 输出：TC-09 至 TC-13、订单查询与管理。

### Phase 5：安全、联调与部署
- 权限测试、端到端验收、备份恢复、生产配置和部署手册。
- 输出：TC-14 至 TC-16、部署文档、已知限制清单。

每个阶段必须通过代码评审、自动化测试和验收后再进入下一阶段。禁止在库存与订单一致性尚未验证时直接开始 UI 美化或宣称具备生产级秒杀能力。

## 16. 需要在开发前确认的决策

1. 数据库选型及版本：本文建议 MySQL 8.x。
2. 后端持久化方式：Spring JDBC 或 MyBatis 选定一种主方案，避免多种 ORM 混用。
3. 用户登录方式、Token 生命周期、管理员初始化方式。
4. 活动取消时，已存在待支付订单的处理政策。
5. 商品下架后，已发布/进行中的活动是否立即停止新订单。
6. 限购规则是否固定为同用户同活动最多一件已支付商品。
7. 模拟支付仅用于本地/测试环境，还是作为受控演示模式部署。
8. 是否允许管理端上传图片，及图片存储方案。
9. 生产环境部署平台、域名、TLS、备份周期和恢复目标。
10. 经压测确定目标并发量和性能目标；在测试前不承诺具体 QPS。

## 17. 完成定义（Definition of Done）

每个功能只有同时满足以下条件才算完成：

- 需求和业务规则有文档。
- 输入验证、权限检查、错误码完整。
- 领域规则与事务边界明确。
- 数据库变更有版本化迁移脚本。
- 自动化测试覆盖正常、异常、边界和并发路径。
- 日志和审计不泄露敏感信息。
- Android/Vue 与 OpenAPI 契约一致。
- 本地可按 README 复现构建与测试。
- 未完成项和已知限制如实记录。
